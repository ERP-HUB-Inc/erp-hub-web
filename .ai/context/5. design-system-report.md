# Report Design System — Draft

## Purpose and scope

Use this guide when building or updating report pages across MarketChain ERP: sales, purchases, inventory, financial reports, and future reporting modules. It defines the shared visual style that reports should follow.

Purchase Report is a visual reference for this guide. Its tab names, metrics, filters, formulas, and pagination settings are specific to that feature and are not requirements for other reports.

Follow [2. design-system.md](2.%20design-system.md) for the application UI stack, component compatibility, brand variables, accessibility, and shared behavior. Report business rules belong in the relevant [report feature documents](../features/reports/).

This is a proposed shared design standard derived from existing source styles, not an implemented global component library or token system. Existing reports may differ. Apply it to new report pages and requested design updates; avoid restyling unrelated screens during a small fix. Browser appearance and computed styles still need visual review.

## Visual direction

Create a calm, readable dashboard with a pale canvas, rounded white panels, subtle borders and shadows, compact labels, and prominent values. Keep filters easy to scan and tables dense enough for comparing business data.

Use the primary teal color (`#14b8a6`) for active report tab underlines and primary actions. Use pastel icon backgrounds to distinguish summary metrics. Status colors must retain their domain meaning and always appear with readable text or an icon.

## Page composition

Use this reading order as the default:

```text
Report title + short description
Report tabs (when multiple views are needed)
Date range + relevant context filters + report action
Summary cards (when useful)
Section heading + explanation or comparison period
Chart, insight panel, or detailed table
Table footer and pagination (when needed)
```

- Keep the title, filters, summaries, and content aligned to the same page edges.
- Use tabs for distinct report views. A single-view report does not need tabs.
- Put view-specific filters and summaries inside the relevant tab. Shared filters may sit above the tabs when they govern every view.
- Show only metrics and controls that support the report's purpose. Card count and filter selection follow the report requirements.
- Use charts when they make trends or comparisons easier to understand. Table-only reports are valid.
- Avoid unnecessary nested cards around headings or every small group of values.

| Mobile page padding | `16px` |

| Supporting text | `#8885a7` |

| Subtitle/body description | `13px` |

Inherit the application's existing English and Khmer fonts. Keep supporting text readable and check contrast against the actual surface, especially for small labels. Allow long labels and translated text to wrap.

## Panels and tabs

The standard report shell uses:

- White panels with an `18px` radius.
- Border: `1px solid rgba(196, 190, 220, 0.7)`.
- Shadow: `0 10px 24px rgba(42, 34, 85, 0.04)`.
- Tab-panel padding: `0 20px 20px`.
- Tab labels: `13px`, weight `600`, muted supporting text color.
- Active/hover tab text: `#17152b`.
- Active underline (bottom indicator): `2px`, `var(--primary-color, #14b8a6)`.
- Tab spacing: `18px` right margin and `14px 0 12px` padding.

Keep active navigation clear through both text treatment and the underline. Preserve Ant Design keyboard and focus behavior.

Use the application's primary color variable for the active tab underline across all report pages. The primary color is `#14b8a6`; do not override the active indicator with purple (`#6c4cff`). Purple may still be used for metric accents.

For Ant Design 3, the active bottom indicator is `.ant-tabs-ink-bar`. Apply the following pattern beneath the owning report root, replacing `.report-page` with that report's actual root selector:

```css
.report-page .ant-tabs-ink-bar {
    height: 2px;
    background: var(--primary-color, #14b8a6);
}
```

Keep the tab-bar divider separate from the active indicator. If a custom tab implementation uses `border-bottom` for its active state, use the same primary color for that active border. Check local overrides and computed styles so the visible indicator remains teal.

## Statistic cards

Use the Stock Risk statistic-card presentation as the shared standard for new report statistic cards and requested card design updates. Purchased Items and Suppliers now reuse this style. Keep the same surface, uppercase heading, neutral icon tile, large value, supporting detail, and skeleton treatment across report modules.

```text
White statistic card
  Uppercase metric label                 Neutral icon tile
  Prominent formatted value
  Muted context, comparison, or scope note
```

| Property | Standard statistic card |
| --- | --- |
| Surface | White, `1px solid #e1e7ef` border |
| Corner radius | `12px` |
| Shadow | `0 3px 12px rgba(15, 23, 42, 0.03)` |
| Minimum height | `190px`; allow growth for longer content |
| Internal padding | `18px` |
| Grid gap | `16px` |
| Grid bottom spacing | `16px` |
| Heading layout | Flex, space-between, align-start, `8px` gap, `34px` minimum height |
| Heading typography | `11px`, weight `700`, uppercase, `0.04em` letter spacing, `#64748b` |
| Icon tile | `30 × 30px`, `8px` radius, `#f1f5f9` background, neutral `#64748b` icon |
| Icon size | `16px` |
| Value layout | Flex with wrapping, baseline alignment, `6px` gap, `12px 0 8px` margin |
| Main value | `30px`, weight `700`, line-height `1.25`, `#17243b` |
| Supporting detail | `12px`, line-height `1.6`, `#64748b`, wrapping with `6px` gaps |

### Content and states

- Keep the label and icon in the header, the value below, and supporting context beneath the value. Give values the full available width instead of squeezing them beside a large icon.
- Preserve domain formatters for currencies, quantities, signs, and percentages. Allow long values to wrap; avoid clipping or ellipsis on essential figures.
- Explain the scope with useful detail, such as “For selected report filters”, or show an existing domain comparison. Do not invent trends, percentages, or business conclusions to fill space.
- Use a neutral card by default. Do not add decorative colored bottom strips, pastel metric tiles, or different card geometry per report.
- Apply semantic colors or a tinted card only when an established domain condition requires emphasis. Stock Risk's excess-stock card is an existing example. Pair color with a readable status or explanation.
- Do not infer favorable or unfavorable outcomes from a number's sign alone. Missing data must remain distinguishable from zero.
- Use Ant Design `Skeleton` inside the card with `active`, `title={false}`, and `paragraph={{ rows: 3 }}` while loading. Keep the card dimensions stable and hide stale figures during loading. Mark the summary group with an accessible name and `aria-busy`.

### Responsive layout and reuse

Use the metric count and available width to choose the grid. Maintain equal card heights within a row, and reduce columns before labels or values become cramped. The six-card Purchased Items/Suppliers layout uses six columns from `1600px`, three from `1200px`, two from `576px`, and one below `576px`. Reports with different metric counts may use a different grid while preserving the card style.

Within Purchase Report, reuse the existing `.stock-risk-card`, `.stock-risk-card-heading`, `.stock-risk-icon-tile`, `.stock-risk-card-value`, and `.stock-risk-card-detail` classes, as `SummaryCards` does in `PurchaseReportParts.jsx`. The owning report already loads `stockRisk.css`.

For other report modules, reuse a compatible shared component if available. If these styles need to be reused across modules, extract the presentation into a shared report component/stylesheet rather than importing a Purchase feature stylesheet into another module. No global statistic-card component has been introduced by this guide.

Cost Changes currently uses a related compact variant (`158px` minimum height, `20px` padding, a plain header icon, and a `32px` value). Treat it as an existing variant; use the standard above for new cards and explicit alignment tasks. Existing variants should not be restyled during unrelated fixes.

## Filter toolbar and actions

- Use a horizontal flex toolbar with wrapping, a `10px` gap, and `16px 0` margins.
- Use `36px` high date/select/number controls, `10px` corners, white backgrounds, and `#ded9ee` borders.
- Use `13px` control and action text.
- Size controls for their labels and values. Avoid copying fixed widths from another report without checking the content.
- Keep the date range and most relevant context filters first, followed by the related action.
- Use a quiet bordered button for secondary refresh actions. Use a filled teal button when recalculation or applying filters is the primary action.
- Primary actions use `var(--primary-color, #14b8a6)` and the existing hover/focus treatment using `var(--secondary-cyan, #06b6d4)`.
- Show loading on the relevant action and prevent duplicate requests while it is pending.
- Provide visible labels or accessible names for date ranges, selects, threshold inputs, and search fields.

Preserve the target report's date format and filter behavior. This guide does not decide whether filters apply immediately or require an Apply action, which defaults they use, or whether they are stored in the URL.

### Backend-searchable record selects

For record-backed filters such as location/store/warehouse, category, inventory item, or supplier/vendor, use the shared stateful selects exported from [src/components/stateful/index.jsx](../../src/components/stateful/index.jsx). Users must be able to search the backend for records that are absent from the initially loaded options.

| Record type | Existing component |
| --- | --- |
| Location / store / warehouse | `SelectLocation` |
| Category | `SelectCategory` |
| Inventory item / product | `SelectItem` |
| Supplier / vendor | `SelectVendor` |

- Reuse these components instead of building a report-local select from a fixed initial list. Increasing the initial fetch limit or filtering only the loaded options does not replace backend search.
- Inspect the selected component's supported props before integrating it. Preserve the report's selected IDs, labels, clear/All behavior, and filter semantics; the existing selects do not all share the same props or default values.
- If the required record type has no suitable select, implement a reusable backend-searchable select in `src/components/stateful/` and export it from `src/components/stateful/index.jsx`. Extend an existing component there when the record type already exists but needs additional capabilities.
- Shared select implementations should debounce remote searches, prevent stale results from replacing newer results, and handle loading, empty, and error states. Keep selected records readable even when they are outside the current result list, and preserve accessible names and keyboard behavior. Verify these behaviors when reusing or extending a component; this guide does not imply every existing select already implements them.
- Static choices such as report status, grouping, sort order, or page size can use ordinary selects. Record filters such as category must still use the shared backend-searchable component rather than deriving their only options from the visible report rows.

When reviewing a record filter, search for a valid record outside the initial result set and confirm it can be found and selected. Also check clearing the filter and restoring an existing selection.

## Report action buttons

Use the following button styles when adding an action to any report page. Choose emphasis according to the action's role and keep button styling consistent within the view.

| Action type | Examples | Style |
| --- | --- | --- |
| Primary | Apply filters, Generate report, Recalculate | Filled `var(--primary-color, #14b8a6)` background and border, white text; cyan hover/focus using `var(--secondary-cyan, #06b6d4)` |
| Secondary | Refresh, Reset filters, Export, Print | White background, `1px solid #ded9ee` border, `#17152b` text; teal border/text on hover/focus |
| Row action | View details, Review item | Compact bordered button, `6px` radius, `12px` text, `#dbe4ee` border and `#334155` text; teal border/text on hover/focus |
| Destructive | Delete a saved report or remove a configuration, when supported | Existing Ant Design 3 `type="danger"` treatment; preserve the application's confirmation and permission rules |

Export and Print are normally secondary actions. Promote an action only when it is the main purpose of that view. Keep one primary action per action group where possible.

### Size, spacing, and placement

- Page and toolbar buttons: `36px` height, `10px` radius, `13px` text, weight `600`, and approximately `14px` horizontal padding. Allow width to grow with the label.
- Table row buttons: use Ant Design `size="small"` with the row-action styling above; keep the action column wide enough for the label.
- Use an `8px` gap between adjacent buttons and a `6px` gap between an icon and its label when the component does not already provide spacing.
- Place report-wide actions beside the page heading or at the end of the filter toolbar, according to the existing layout. Put row actions in a consistently aligned action column.
- Let action groups wrap on small screens. Keep labels readable and avoid clipping icons, translated text, or keyboard focus outlines.
- Use clear verb labels such as “Export”, “Print”, “Refresh”, or “View details”. Use the existing Ant Design 3 icon API, for example `icon="download"`, `icon="printer"`, or `icon="reload"`.

### Interaction and implementation

- Use the existing Ant Design `Button` or a compatible shared wrapper. Check which props a wrapper forwards before relying on `size`, `loading`, `disabled`, or accessibility props.
- Use `htmlType="button"` for non-submit actions inside forms. Use a real link or React Router `Link` for navigation and a button for operations.
- Use `loading` and `disabled` while the action is pending. Preserve the library's muted disabled appearance; enabled hover styles must not override disabled buttons.
- Preserve a visible keyboard focus indicator. A report-scoped `:focus-visible` outline may use `2px solid var(--primary-color, #14b8a6)` with a `2px` offset.
- Icon-only actions need an accessible name; add a tooltip when the icon's meaning is unclear. Prefer a visible label for important actions.
- Preserve existing permission checks and report feedback patterns. Show failures clearly and restore the action so users can retry.
- Scope overrides beneath the report root and use modifier classes for primary, secondary, or row actions. These styles are guidance; they do not imply a shared `ReportButton` component already exists.

## Data-table standard

Use this standard for new report tables and requested table design updates across all reporting modules. It combines the panel, toolbar, detailed-cell, and pagination patterns in Cost Changes, Stock Risk, and Purchase vs Sales into one shared presentation. Their existing styles differ slightly; the values below are the chosen defaults for future work, not a claim that every current table already matches them.

### Structure and surface

```text
White table panel
  Toolbar: heading / result context + table filters + search
  Table: column headers + data rows / loading / empty state
  Footer: visible row range + optional page size + pagination
```

Keep the toolbar, table, and footer within one panel. Do not put each in a separate card or add a second outer border around the table.

| Element | Standard treatment |
| --- | --- |
| Panel surface | White, `1px solid #e1e7ef` border, `12px` radius |
| Panel shadow | `0 3px 12px rgba(15, 23, 42, 0.03)` |
| Toolbar/footer padding | `18px` desktop; `12px` at widths up to `767px` |
| Toolbar/footer layout | Flex, wrap, center alignment, space-between, `12px` gap |
| Table heading | `14px`, weight `700`, `#17243b` |
| Table body text | `13px`, `#0f172a` |
| Supporting text | `11–12px`, `#64748b` |
| Header background | `#f8fafc` |
| Header text | `11px`, weight `600`, `#64748b`, uppercase, `0.03em` letter spacing |
| Header padding | `14px 18px` |
| Header bottom border | `1px solid #e2e8f0` |
| Body cell padding | `22px 18px` |
| Body cell alignment | Vertically centered, line-height `1.6` |
| Body row separator | `1px solid #eef2f7` |
| Row backgrounds | White; subtle even-row stripe `#fbfcfe` |
| Row hover | Light tint; retain the current global `#e6f7ff` hover treatment |
| Table body minimum height | `240px` for a stable loading/empty area; allow content to grow |
| Footer divider | `1px solid #e2e8f0` |

The previous compact table pattern uses smaller cells and mixed-case headers. Keep it on unchanged legacy reports; use the detailed standard above when creating a new report table or explicitly standardizing an existing one. Do not mix header styles or row densities inside the same table.

### Toolbar and search

- Keep the heading or category/status controls on the left and search toward the right. Allow wrapping without reducing labels to unreadable widths.
- Use a search icon, a clear action, and an accessible name. A desktop search width around `240–250px` is a starting point; expand it to full width on small screens.
- Use the shared backend-searchable stateful selects for record filters, including categories, as specified above. Static status/activity choices may use ordinary selects or category buttons.
- Category buttons should include text and optional counts. Show selected styling and `aria-pressed`; use a `2px` primary-teal focus outline with a `2px` offset.
- Keep loaded-detail counts and filtered-row counts distinct from report-wide totals. Label their scope clearly.

### Columns and cell content

- Align identity/name columns left and numeric values right. Place row actions consistently in the final column.
- Use a stable record ID for `rowKey`. Composite keys may be used where the report identifies item/variant pairs; avoid array indexes when stable identifiers are available.
- Give the main entity column enough width for a name plus metadata. The reference tables use approximately `280–340px`; choose actual column widths from the content and available space.
- Display the entity name in bold, with SKU/reference/category metadata below it in muted text. Metadata groups should wrap, with `6px` gaps and approximately `4px` top spacing.
- An optional identity icon tile may use `38–42px` dimensions, a `10px` radius, and a neutral `#f1f5f9` background. Do not add decorative icons to every numeric cell.
- SKU/reference chips use `1px 5px` padding, `4px` corners, `11px` text, `#475569` foreground, and `#f1f5f9` background.
- Keep previous/reference values secondary and current values prominent in comparison cells. Put variance or supporting notes on a second line rather than crowding the main value.
- Use existing currency, quantity, sign, and percentage formatters. Preserve units, unavailable-value placeholders, and the distinction between missing data and zero.
- Keep comparison bars paired with visible quantities and an accessible description. A bar alone must not carry the meaning of a cell.
- Allow long names and identifiers to wrap using `min-width: 0` and appropriate overflow wrapping. Use a tooltip only when essential content is truncated.

### Status badges and row actions

Use compact inline badges: `2px 8px` padding, `6px` radius, `10–11px` text, weight `600–700`, and a `6px` icon/dot gap. Keep short badge labels on one line.

| Semantic tone | Foreground | Background |
| --- | --- | --- |
| Neutral / unavailable | `#64748b` | `#f1f5f9` |
| Positive / healthy | `#0f766e` | `#ecfdf5` |
| Warning / attention | `#92400e` | `#fffbeb` |
| Negative / critical | `#b91c1c` | `#fef2f2` |

Choose the tone from existing domain rules. An increase or decrease is not automatically positive or negative. Pair colors with status text, and explain unavailable data where needed.

Use the compact row-action button style defined in “Report action buttons”. Preserve permission checks, accessible names, and link semantics for navigation. If the required record reference is missing, show a disabled action with a useful explanation.

### Footer and pagination

- Put the visible row range on the left, for example “Showing 1 to 10 of 42 items”, and pagination on the right. For zero results, show a valid zero range.
- Use `12px` muted footer text. Group footer controls with an `8px` gap and let them wrap on mobile.
- If page-size selection is supported, label it “Rows per page”. Default size and available sizes follow the target report's requirements.
- Use compact Ant Design pagination. The active page has `var(--primary-color, #14b8a6)` background and border, white text, and `5px` corners.
- Give optional first/last page icon buttons accessible names. Disable unavailable navigation and prevent paging conflicts while loading.
- Use one pagination control. If the footer owns pagination, set the table's `pagination={false}`.
- Keep pagination correct after filters change or rows disappear: reset or clamp the current page and announce updated row counts with `aria-live="polite"` where appropriate.
- Preserve the report's client/server pagination model. A visual update must not change how many records are fetched or imply that loaded rows represent the entire dataset.

### Loading, empty, scrolling, and implementation

- Use the table's loading state while fetching and retain a stable panel layout. Distinguish “no report data” from “no matches for these filters”. Show section errors and retry behavior using the existing report pattern.
- Use Ant Design 3 `Table` directly or a compatible shared wrapper. Inspect forwarded props before depending on `scroll`, `locale`, `loading`, or custom columns.
- Derive horizontal scroll width from the columns. Keep the toolbar and footer outside the horizontally scrolling body so their controls remain usable.
- Preserve table semantics, keyboard access, focus outlines, and full access to off-screen columns. Avoid overflow rules that clip the scrollbar or focused controls.
- Scope all table overrides beneath the owning report root. The class names above describe patterns; no shared report data-table component or stylesheet is implied.
- Global table styles include striping and hover rules with `!important`. Check the rendered cascade before adding local overrides. Do not introduce additional global table rules to fix one report.

Reference differences: Cost Changes uses `14px 18px` headers and `22px 18px` body padding; Stock Risk uses `14px 16px` and `22px 16px`; Purchase vs Sales uses a blue-tinted `#eff6ff` header and `24px 18px` body padding. Use these implementations for cell composition and interaction examples, and follow the shared defaults above for a consistent new table design.

## Charts, comparisons, and insights

- Use consistent series colors, legends, tooltip formatting, and axis labels across related views.
- Keep chart panels in the same row visually balanced. Allow enough height for labels and legends.
- Place comparison-period text beside or below the section heading; use smaller supporting text and allow wrapping.
- Put explanations near the figures they clarify. Clearly label the period, units, and scope of a comparison.
- Use a subtle tinted panel for context. Reserve warning and error alerts for conditions that warrant them.
- Pair badges and status colors with text. Do not invent thresholds or business classifications to match a visual reference.

## Loading, empty, and error states

- Use Ant Design card loading states or skeletons for summary areas and table loading feedback for rows. Preserve a stable layout during loading.
- Show errors near the affected section with a clear message and a retry action when available.
- Keep filter values on failure so the user can retry without repeating their selection.
- Distinguish an empty report from a search/filter with no matches. Provide a useful next step, such as adjusting the date range or clearing local filters.
- Show unavailable figures explicitly. Do not substitute zero or success styling for missing data.
- Keep page-count announcements accessible, and retain keyboard focus and selected-filter states.

## Responsive, theme, and style ownership

- Reduce page padding to `16px` at widths up to `767px`.
- Let toolbars wrap and make controls full width where necessary on small screens.
- Reduce summary-card columns before values or labels become cramped.
- Keep wide tables scrollable within their panels; avoid horizontal scrolling of the entire page.
- Check English and Khmer labels, long entity names, large values, and keyboard focus on small and large screens.
- Scope styles beneath the owning report's root class or ID. Reuse shared components where compatible; do not import a feature stylesheet solely to borrow unrelated styles.
- Treat the values above as light-theme guidance. Follow the [dark-theme plan](../features/dark-theme.md) when implementing dark surfaces, text, and borders; keep print/export surfaces appropriate for their document format.

## Review checklist

- Does the report follow the shared canvas, typography, spacing, and chosen panel treatment?
- Does the active tab bottom indicator use the primary color `#14b8a6`?
- Are filters, summaries, section headings, and detailed content easy to scan?
- Do statistic cards follow the shared Stock Risk presentation, including neutral tiles, typography, spacing, and skeleton loading?
- Do record-backed filters use shared stateful selects and find records outside the initial option list?
- Does the data table follow the shared panel, header, row, cell, toolbar, and pagination standard?
- Are essential values readable without clipping or misleading formatting?
- Do labels explain status colors, comparisons, units, and data scope?
- Are loading, empty, unavailable, and error states clear?
- Do action buttons use the correct emphasis, size, placement, and loading/disabled states?
- Do controls, focus states, cards, and tables work on small and large screens?
- Are styles scoped and existing business rules and permissions preserved?
